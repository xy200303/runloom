# 技术设计文档

## 定位

Runloom 是一个本地优先、可复用、可成长的动态 agent runtime，也是一款专业编程开发工具。它的首要使用场景是像 Codex / Claude Code 一样在真实代码仓库中协助开发者完成项目理解、代码修改、测试修复、审查和交付。

Runloom 面向开发者提供三个 npm 包：

- `runloom-agent`：headless agent runtime，是系统核心。
- `runloom-tui`：终端交互界面和 CLI。
- `runloom-web`：后期实现的 Web server/API/SSE/WebSocket 展示层和 Vue 组件包。

未来横向扩展还需要支持 VSCode 插件、local daemon、CI bot 和其他 IDE。它们都必须复用 `runloom-agent`，通过 host adapter 和事件流接入，不能重写 runtime。

Runloom 不以 DAG workflow 为中心，不实现 WorkflowPatch、workflow version graph 或显式 workflow runtime。任务执行由一个隐式动态 agent loop 驱动：模型根据目标、上下文、todo、工具结果和安全策略持续决定下一步。

长期目标是把 Runloom 做成用户本地的 agent runtime 和开发工作台：它可以理解项目、修改文件、沉淀经验、生成工具、生成 skill、评估自己的改进，并与其他 agent 协作。

## 专业编程开发工具定位

Runloom 的产品体验应优先服务软件工程闭环，而不是泛用问答。首期必须把以下能力作为一等能力设计：

- 项目理解：读取 package、配置、源码结构、测试结构、依赖和入口文件，形成可追溯的项目摘要。
- 任务规划：把用户目标拆成 todo，并在执行中持续更新。
- 代码定位：通过文件搜索、符号搜索、调用关系、错误日志和测试输出来定位相关代码。
- 文件编辑：支持小范围 patch、批量修改计划、修改前后 diff 和回滚线索。
- 测试验证：运行类型检查、单元测试、构建命令或用户指定验证命令，并把失败结果带回 loop。
- Git 感知：读取 git status、diff、当前分支和未提交变更，避免覆盖用户改动。
- 代码审查：能以 review 姿态指出 bug、回归风险、缺失测试和 public API 风险。
- 交付说明：结束时说明改了什么、验证了什么、还有什么风险。
- 安全控制：所有写文件、shell、git、外部 agent、自我演化都经过权限策略、approval、audit 和可回滚设计。

非目标：

- 不把 Runloom 做成只会聊天的助手。
- 不把首期重点放在泛业务自动化、营销页面或非开发类工作流。
- 不用显式 DAG workflow 替代动态 agent loop。

## 参考边界

本地 coding agent 的工程经验验证了几个关键方向：

- 本地 workspace 加模型配置加工具调用是一条可行主线。
- TUI 应只负责交互、事件渲染、命令和状态展示。
- API/Gateway/TUI 应共享同一套 agent 核心和工具注册。
- 工具必须有开关、权限、超时、allowed roots 和审计。
- SSE 事件回放、后台 run 和 session store 对真实使用非常重要。

Runloom 在此基础上升级为多包 npm runtime，并把模型协议适配、Skills、MCP、A2A、本地成长、自我演化和 eval gate 作为核心设计对象。

## 总体架构

```text
applications / embedders
  |
  | import runloom-agent
  | run runloom-tui CLI
  | attach future runloom-vscode extension
  | mount runloom-web server/components (future Vue implementation)
  v
runloom-agent
  runtime/
  coding/
  host/
  providers/
  tools/
  skills/
  mcp/
  a2a/
  external-agents/
  memory/
  growth/
  evolution/
  evals/
  sessions/
  approvals/
  events/
  security/
  observability/
  prompts/
```

数据流：

1. 用户或宿主应用提交目标。
2. runtime 创建或恢复 session。
3. planner 根据目标、context、todo、skills、memory 和 policy 生成下一步。
4. provider 以统一协议调用模型，产出文本、reasoning、tool call 或 structured output。
5. tool executor 对工具调用做权限判断、approval、trace、redaction、timeout 和执行。
6. runtime 将结果追加到消息上下文和事件流，更新 todo。
7. loop 持续运行，直到完成、被用户中止、达到限制或进入等待审批状态。
8. 任务结束后触发 reflection、memory curation、eval 或成长提案。

开发任务的典型闭环：

```text
understand goal
  -> inspect workspace and git state
  -> create todo
  -> locate relevant files
  -> propose edit plan when risk is non-trivial
  -> apply patch through guarded tool
  -> run verification commands
  -> inspect failures and iterate
  -> summarize diff, tests, risks, and next steps
```

## pi-agent 集成方式

`runloom-agent` 应把 pi-agent 视为底层可替换执行引擎之一，而不是把外部 API 暴露成 Runloom public API。

建议结构：

- `runtime/PiAgentLoopDriver` 负责把 Runloom 的 messages、tools、policy 和 provider bridge 转换给 pi-agent。
- `providers/PiModelBridge` 负责连接 Runloom `ModelProvider` 和 pi-agent 需要的模型接口。
- `tools/PiToolBridge` 负责把 Runloom `ToolDefinition` 暴露给 pi-agent，同时拦截 tool call 进入 Runloom approval/security/trace。
- `events/PiEventAdapter` 负责把 pi-agent 原始事件转成 `RunloomEvent`。

约束：

- public API 不导出 pi-agent 原始类型。
- runtime 业务逻辑不直接依赖某个供应商 SDK。
- 如果未来替换或并行支持其他 loop driver，不影响 TUI/Web 和第三方接入。

## 横向扩展与 VSCode 插件准备

Runloom 必须从首期开始保持 host-agnostic。`runloom-agent` 不依赖 TUI、Vue、VSCode API 或任何 IDE SDK，而是通过宿主适配接口接入不同界面和运行环境。

核心抽象：

```ts
export interface RunloomHostAdapter {
  kind: "tui" | "vscode" | "web" | "daemon" | "ci" | "custom";
  workspace: WorkspaceAdapter;
  terminal?: TerminalAdapter;
  diff?: DiffAdapter;
  approvals?: ApprovalBridge;
  diagnostics?: DiagnosticsAdapter;
}
```

VSCode 插件后期只负责：

- 把 VSCode workspace、multi-root、diff editor、integrated terminal、diagnostics、secrets 和 command palette 适配为 Runloom host adapter。
- 展示 transcript、todo、coding activity、approval 和 diff。
- 把用户操作通过 `runloom-agent` public API 回传。

VSCode 插件不负责：

- agent loop。
- 模型 provider。
- 工具权限和 approval policy。
- session store 业务逻辑。
- MCP/A2A/自我演化实现。

首期需要预留：

- workspace/terminal/diff/approval/diagnostics adapter 类型。
- coding events，例如 `coding.diff.created`、`coding.verification.completed`、`coding.git.status`。
- event replay 和 session resume/cancel。
- approval 可跨 UI 处理。
- runtime 生命周期不绑定 TUI 进程。

## 动态 Agent Loop

Runloom 的 loop 是隐式、事件驱动、可恢复的：

```text
submit(goal)
  create run
  load session, workspace summary, memory, skills, policy
  append user message
  while not done:
    emit run.step.started
    compact context if needed
    ask model provider for next action
    normalize model event stream
    if text/reasoning:
      append assistant output
      emit transcript events
    if tool call:
      classify risk
      request approval if required
      execute tool through guard
      append tool result
      update todo if needed
    if structured todo update:
      validate and store todo
    if completion signal:
      finalize run
  trigger post-run reflection and optional growth proposal
```

终止条件：

- 模型明确完成任务。
- todo 全部完成并通过最终检查。
- 用户中止。
- 达到最大轮数、最大 token、最大时间或最大工具调用数。
- 工具或模型错误不可恢复。
- 等待用户 approval。

## 统一事件模型

Runloom 的统一事件模型可以基于 OpenAI Responses API 的 streaming event 思路设计，但不能直接把 OpenAI 的事件作为内部唯一模型。推荐做法是：

- 模型输出层采用接近 OpenAI Responses 的 `response.*` 语义，例如文本 delta、reasoning delta、tool call 参数增量、完成、失败和 usage。
- Runtime 领域层使用 Runloom 自己的事件命名，例如 `tool.*`、`approval.*`、`todo.*`、`mcp.*`、`a2a.*`、`external_agent.*`、`memory.*`、`evolution.*`、`eval.*`。
- Web/API 层可以提供 OpenAI Responses compatible stream 投影，但内部 store、TUI/Web 和 audit 仍消费完整 `RunloomEvent`。

这样 OpenAI Responses adapter 可以近似直连映射，OpenAI Chat Completions、Claude Messages 和 Gemini adapter 也能统一转换到同一套模型输出事件；同时 Runloom 的 approval、todo、MCP、A2A、本地成长和自我演化不会被供应商 API 限制。

所有 UI、API、外部 agent、MCP 和审计都消费同一种 `RunloomEvent` envelope：

```ts
export interface RunloomEventEnvelope<TPayload = unknown> {
  id: string;
  type: string;
  runId: string;
  sessionId: string;
  sequence: number;
  timestamp: string;
  source:
    | "model"
    | "runtime"
    | "tool"
    | "approval"
    | "mcp"
    | "a2a"
    | "external_agent"
    | "memory"
    | "evolution"
    | "eval";
  payload: TPayload;
}
```

首期事件类型建议：

```ts
export type RunloomEvent =
  | RunStartedEvent
  | RunStepStartedEvent
  | ResponseOutputTextDeltaEvent
  | ResponseReasoningDeltaEvent
  | ResponseToolCallDeltaEvent
  | ResponseCompletedEvent
  | ResponseFailedEvent
  | ToolCallRequestedEvent
  | ToolCallStartedEvent
  | ToolCallCompletedEvent
  | ToolCallFailedEvent
  | ApprovalRequestedEvent
  | ApprovalResolvedEvent
  | ApprovalPolicyUpdatedEvent
  | TodoUpdatedEvent
  | MemoryUpdatedEvent
  | SkillActivatedEvent
  | ExternalAgentDelegatedEvent
  | EvalRunUpdatedEvent
  | EvolutionProposalCreatedEvent
  | RunCompletedEvent
  | RunFailedEvent;
```

事件命名分层：

```text
response.*          模型输出层，尽量贴近 OpenAI Responses 的事件语义
run.*               Runloom run 生命周期
tool.*              工具请求、执行、结果和失败
approval.*          审批请求和审批结果
todo.*              todo 状态变更
session.*           session 创建、恢复、分支和归档
mcp.*               MCP server、resource、prompt 和 tool 状态
a2a.*               A2A discovery、delegation 和 result exchange
external_agent.*    Codex、Claude Code 等外部 agent 协作
memory.*            memory/reflection/curation 状态
evolution.*         自我演化 proposal、验证、接受和回滚
eval.*              benchmark 运行、评分和 gate 结果
```

事件要求：

- 每个事件有 `id`、`runId`、`sessionId`、`sequence`、`timestamp`、`type`。
- 事件可持久化和回放。
- 事件 payload 必须先 redaction，再写入可外发流。
- UI 渲染不解析供应商原始响应。
- trace/audit 可以引用内部 span，但 public event 保持稳定。
- OpenAI Responses compatible stream 是可选投影，不是内部真实事件存储格式。

## Todo 管理

Todo 是 runtime 的一等状态，不是纯文本列表。

建议类型：

```ts
export interface RunloomTodoItem {
  id: string;
  title: string;
  status: "pending" | "in_progress" | "blocked" | "completed" | "cancelled";
  priority?: "low" | "normal" | "high";
  evidence?: string[];
  updatedAt: string;
}
```

规则：

- 复杂任务开始后必须创建 todo。
- 同一时间最多一个 `in_progress`，除非任务显式允许并行委托。
- todo 更新必须产生 `todo.updated` 事件。
- 完成任务前需要最后一次 todo 状态自检。
- TUI/Web 只显示状态，不自行推导任务进度。

## Session 与 Store

Session 需要支持恢复、分支和事件回放。

核心对象：

- `Session`：长期会话容器。
- `Run`：一次目标提交后的执行过程。
- `MessageSnapshot`：模型上下文快照。
- `TranscriptItem`：面向 UI 的文本和工具 activity。
- `RunloomEventRecord`：可回放事件。
- `AuditRecord`：安全和高影响动作记录。

首期存储可采用本地 SQLite 或文件存储抽象，public API 暴露 `RunloomStore` 接口，默认实现写入 `~/.runloom/session.db`。

## 全局配置与模型路由

Runloom 需要在用户级 `.runloom` 目录中提供全局配置。默认位置是 `~/.runloom/config.json`，用于保存非敏感偏好、默认 provider、默认模型、任务画像和模型路由规则。API key、token、cookie 和其他 secret 不写入该文件，应通过环境变量、系统 keychain、VSCode SecretStorage 或宿主提供的 secret adapter 读取。

仓库内可以存在 `.runloom/config.json` 作为项目级覆盖，但它只能覆盖非敏感配置。优先级从高到低为：

1. 用户在本次任务中显式指定的模型或任务画像。
2. workspace `.runloom/config.json`。
3. 用户全局 `~/.runloom/config.json`。
4. Runloom 内置默认值。

推荐配置结构：

```json
{
  "model": {
    "default": "openai:gpt-4.1",
    "profiles": {
      "frontend_design": "kimi:<frontend-design-model>",
      "go_development": "<provider>:<go-development-model>",
      "prototype_design": "<provider>:<prototype-design-model>"
    },
    "routes": [
      {
        "when": { "taskType": "frontend_design" },
        "model": "kimi:<frontend-design-model>"
      },
      {
        "when": { "language": "go" },
        "model": "<provider>:<go-development-model>"
      },
      {
        "when": { "taskType": "prototype_design" },
        "model": "<provider>:<prototype-design-model>"
      }
    ]
  }
}
```

模型路由由 `runloom-agent` 解析，不由 TUI、Web 或 VSCode 插件自行实现。runtime 在每次 run 开始时根据任务描述、workspace 语言信号、用户显式 profile 和 host adapter 传入的上下文选择模型，并产生可审计的 `model.selection.resolved` 事件。事件只记录 provider、model、命中规则和原因，不记录 secret。

模型路由必须遵守以下原则：

- `provider:model` 是逻辑标识，不等同于供应商原始 API URL；具体 base URL、认证和协议由 `ModelProvider` 管理。
- 同一个任务过程中默认不自动切换模型，除非用户显式允许或模型不可用需要降级。
- 不同任务类型可以使用不同模型，例如前端设计、Go 开发、原型设计、代码审查、测试修复。
- route 匹配失败时回退到 `model.default`。
- 任务画像和 route 命中必须进入 run metadata，方便回放、评估和问题排查。
- Host adapter 可以展示和修改配置，但不直接读写 `.runloom` 内部文件，必须通过 agent public API。

## Approval 机制

Approval 是 `runloom-agent` 的核心权限决策层，不是 UI 弹窗的附属功能。用户可以修改权限审批方式，Runloom 首期支持三种模式：

| 模式 | API 值 | 行为 |
| --- | --- | --- |
| 完全访问 | `full_access` | 在用户配置的 workspace、allowed roots、工具白名单和硬性安全规则内自动放行，不弹出逐次审批 |
| 请求批准 | `ask` | 命中该权限范围的动作必须产生 `approval.requested` 并等待用户决定 |
| 替我决定 | `auto_decide` | Runloom 根据风险等级、用户偏好、任务上下文和历史决策自动允许或拒绝；高不确定性或 critical 动作仍可升级为请求批准 |

完全访问不是无护栏模式。以下 hard deny 永远不能被模式绕过：

- 访问 denied roots 或 workspace 外未授权路径。
- 读取或外发已识别 secret。
- 执行明确禁用的危险命令。
- 绕过 redaction、audit trail 或 trace。
- 修改关键 identity、注册新 tool/skill、扩大权限、自我发布等 critical 动作，除非用户对该具体 scope 显式配置允许。

所有高风险动作都必须进入统一 approval/policy 决策：

- 写文件、删除文件、移动文件。
- shell、网络、浏览器、GUI、MCP tool。
- 外部 agent 委托。
- 新增或修改 tool/skill。
- 修改 identity 文件。
- 扩大权限。
- 自我代码修改、升级、回滚。

approval 不是 UI 逻辑，而是 `runloom-agent` 的可订阅状态：

```ts
export type ApprovalMode = "full_access" | "ask" | "auto_decide";

export type PermissionScope =
  | "filesystem.read"
  | "filesystem.write"
  | "filesystem.delete"
  | "shell"
  | "network"
  | "browser"
  | "gui"
  | "mcp.tools"
  | "external_agents"
  | "a2a.delegation"
  | "memory.write"
  | "identity.write"
  | "tools.register"
  | "skills.register"
  | "evolution.apply"
  | "npm.publish";

export interface ApprovalPolicyConfig {
  defaultMode: ApprovalMode;
  scopes: Partial<Record<PermissionScope, ApprovalMode>>;
  updatedAt: string;
  updatedBy: "user" | "host_app" | "migration";
}

export interface ApprovalRequest {
  id: string;
  runId: string;
  scope: PermissionScope;
  action: string;
  risk: "low" | "medium" | "high" | "critical";
  mode: ApprovalMode;
  summary: string;
  details: unknown;
  expiresAt?: string;
}

export interface ApprovalDecision {
  decision: "approved" | "denied";
  reason?: string;
  remember?: "never" | "session" | "workspace" | "global";
  setModeForScope?: ApprovalMode;
}
```

TUI/Web/宿主应用通过 `agent.resolveApproval(id, decision)` 回传决定。用户修改审批方式时，宿主应用调用 `agent.updateApprovalPolicy(policyPatch)`，runtime 必须写入 audit trail 并产生 `approval.policy.updated` 事件。

决策流程：

```text
tool or runtime action
  -> classify permission scope
  -> apply hard deny
  -> load user approval policy
  -> if mode is full_access: auto approve within configured guardrails
  -> if mode is ask: emit approval.requested and wait
  -> if mode is auto_decide: risk policy decides allow/deny/ask
  -> emit approval.resolved or approval.auto_resolved
  -> execute or reject action
  -> write audit trail
```

## 安全护栏

安全层按顺序执行：

1. workspace/path guard：限制文件访问根目录。
2. command guard：解析 shell 命令，阻断危险命令和越权参数。
3. permission policy：判断动作是否允许、需要 approval 或拒绝。
4. redaction：对 secret、token、环境变量、私密路径做脱敏。
5. risk classifier：给工具调用、成长提案和外部委托打风险等级。
6. audit trail：记录来源、参数摘要、审批人、结果和回滚线索。

## 可观测性

Runloom 的生产级要求包括：

- 结构化日志。
- trace/span。
- token usage。
- tool latency。
- approval latency。
- provider error classification。
- retry 和 backoff。
- audit trail。
- eval score 历史。

`runloom-agent` 应允许宿主应用注入 logger、tracer、meter 和 redactor。

## 错误处理

错误分为：

- `ProviderError`：模型 API、限流、网络、鉴权、内容安全。
- `ToolError`：schema、权限、超时、执行失败。
- `ApprovalError`：拒绝、过期、取消。
- `StoreError`：持久化失败、迁移失败。
- `SecurityError`：越权、secret 泄露风险、危险操作。
- `RuntimeError`：loop 状态异常、上下文损坏。
- `EvolutionError`：验证失败、eval gate 未通过、回滚失败。

每类错误必须有 machine-readable code、human-readable message 和 recoverability。

## 首期验收

首期不需要完整实现自我成长闭环，但必须做到：

- `runloom-agent` 和 `runloom-tui` 能独立 build、typecheck、publish dry run。
- `runloom-agent` 可被 Node.js import，并运行一个最小动态 loop。
- provider 接口稳定，至少有一个真实协议 adapter；测试代码可以提供 test-only provider。
- 支持从 `~/.runloom` 读取全局模型配置，并能按任务画像选择不同模型。
- 具备专业 coding agent 的最小闭环：项目读取、文件搜索、patch、diff、shell 验证、git status、todo 和最终变更摘要。
- 工具调用、approval、todo、session、事件流有最小实现。
- TUI 能消费 `runloom-agent` 事件，而不是重新实现 loop。
- `runloom-web` 不进入首期实现；后期使用 Vue 3 + TypeScript + Vite 实现，并复用同一套 `runloom-agent` public API。
- 单元测试覆盖 config parser、模型路由、provider adapter、tool executor、approval policy、path guard、event bus 和 store。
- 集成测试覆盖真实 workspace 的 agent loop、模型工具调用、TUI 命令、approval 持久化、provider 错误归一化、pack dry run 和不依赖真实供应商的协议适配 fixture。
- docs、README、examples、exports、types、CI/CD 和 changelog 策略齐备。
