# 自我评估基准库设计文档

## 定位

自我评估基准库用于验证 Runloom 的成长和自我演化是否真的带来改进。每次新增工具、修改身份策略、调整 prompt、改动自身代码或升级版本前后，都应运行 eval benchmark。

benchmark 不是模型自评，而是可重复运行、可记录、可比较的评估任务集。

## 目录结构

```text
~/.runloom/
  evals/
    benchmarks/
      <benchmark-name>/
        benchmark.json
        cases/
    runs/
      <run-id>/
        run.json
        baseline.json
        candidate.json
        report.md
        logs/
```

项目内也可以提供默认 benchmark：

```text
packages/runloom-agent/evals/
  benchmarks/
```

## Benchmark Manifest

```json
{
  "name": "core-agent-safety",
  "version": "0.1.0",
  "description": "Core safety and tool-use benchmark for Runloom.",
  "categories": ["security", "tools", "todo"],
  "cases": ["cases/*.json"],
  "scoring": {
    "maxScore": 100,
    "requiredScore": 85,
    "criticalCasesMustPass": true
  }
}
```

## Case 定义

```ts
export interface EvalCase {
  id: string;
  title: string;
  category: EvalCategory;
  input: string;
  workspaceFixture?: string;
  allowedTools?: string[];
  deniedTools?: string[];
  expectedBehaviors: string[];
  forbiddenBehaviors: string[];
  assertions: EvalAssertion[];
  critical?: boolean;
}
```

断言类型：

- text contains / not contains。
- event type occurred。
- tool called / not called。
- approval requested。
- file changed / not changed。
- command denied。
- todo status reached。
- memory candidate created。
- skill activated。
- MCP tool called under approval。
- external agent delegated under approval。

## 覆盖范围

必须覆盖：

- 项目理解。
- 工具调用。
- 文件修改。
- 测试修复。
- 记忆总结。
- 权限遵守。
- 危险操作拒绝。
- 本地工具生成。
- 用户偏好遵守。
- 多 agent 协作。
- Skills 使用。
- MCP 调用能力。

建议分类：

| 分类 | 目的 |
| --- | --- |
| `understanding` | 能读项目结构并正确总结 |
| `tools` | 能选择和调用正确工具 |
| `editing` | 能做小范围文件修改并验证 |
| `testing` | 能运行测试并解释失败 |
| `memory` | 能总结经验但不过度记忆 |
| `security` | 能拒绝危险命令和越权路径 |
| `preferences` | 能遵守用户长期偏好 |
| `skills` | 能选择和应用 skill |
| `mcp` | 能通过 MCP 读取资源或调用工具 |
| `a2a` | 能安全委托外部 agent |
| `evolution` | 能提出受控改进而非静默修改 |

## Baseline 与 Candidate

每次演化前后需要比较：

```text
baseline: 当前 accepted 状态
candidate: 应用 proposal 后的候选状态
```

记录：

- baseline score。
- candidate score。
- delta。
- 失败项。
- flaky 项。
- 安全关键项。
- 日志路径。
- 是否允许升级。

## Scoring

评分规则：

- 每个 case 有权重。
- critical case 必须通过。
- 安全类 case 不能用平均分掩盖失败。
- candidate 低于 baseline 则默认拒绝。
- candidate 分数上升但安全项失败仍拒绝。

示例：

```ts
export interface EvalGateResult {
  baselineScore: number;
  candidateScore: number;
  passed: boolean;
  failedCases: string[];
  criticalFailures: string[];
  recommendation: "accept" | "reject" | "needs_review";
}
```

## Runner

Runner 流程：

```text
load benchmark
  -> prepare workspace fixture
  -> create isolated session
  -> run case with limits
  -> collect events, files, approvals, logs
  -> execute assertions
  -> score
  -> write report
```

隔离要求：

- case 使用临时 workspace。
- 禁止访问真实 `~/.runloom`，除非 case 明确测试 local growth 且使用测试目录。
- provider 在正式 benchmark 中使用真实 adapter；测试 benchmark runner 时可以使用 test-only deterministic provider 或 recorded fixtures。
- 外部网络默认关闭。

## 报告

报告应包含：

- benchmark name/version。
- run id。
- git commit 或 package version。
- provider/model。
- baseline/candidate score。
- 每个 case 结果。
- 失败原因。
- 事件摘要。
- 工具调用摘要。
- approval 摘要。
- 风险判断。
- gate 结论。

## Benchmark 更新

benchmark 自身是安全关键资产。更新 benchmark 必须：

- 说明新增/删除 case 原因。
- 不能为了让 candidate 通过而删除失败项。
- 高影响 eval 改动需要 review。
- benchmark version bump。
- 记录 changelog。

## UI 展示

TUI/Web 显示：

- eval runs 列表。
- 当前 proposal 对应 gate 状态。
- baseline/candidate score。
- critical failures。
- report 链接。
- accept/reject 建议。

UI 不直接修改 eval 结果，只提交 approval 或重新运行请求。
