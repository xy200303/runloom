# Runloom 文档索引

Runloom 是一个使用 TypeScript 开发的生产级本地动态 agent runtime，也是一款面向真实软件工程工作的专业编程开发工具。它的产品方向接近 Codex / Claude Code：在用户本地工作区中理解项目、规划修改、编辑代码、展示 diff、运行测试、修复失败、维护 todo，并在安全边界内持续完成开发任务。

Runloom 的核心不是 DAG workflow，也不是显式 workflow graph，而是 Codex / Claude Code 风格的隐式动态执行循环：agent 持续理解目标、维护 todo、调用工具、读取结果、调整计划，并在安全边界内完成任务。

本目录只描述设计与规划，不代表已经完成全部实现。实现阶段必须以这些文档作为边界和验收依据。

## 设计原则

- `runloom-agent` 是唯一实现 agent runtime 逻辑的包。TUI 和 Web 只消费事件与 API。
- 代码组织必须保持职责清晰、依赖单向、实现简洁；避免过度耦合、过度封装和没有真实复用价值的抽象。
- Runloom 首先是专业编程开发工具，不是泛用聊天机器人；首期能力优先服务代码理解、文件编辑、diff、测试、git 状态、审查和安全回滚。
- `runloom-agent` 必须为横向扩展预留 host/workspace/terminal/diff/approval adapter，未来 VSCode 插件只做宿主适配和 UI，不重写 runtime。
- 所有模型协议都必须通过统一 `ModelProvider` 转换为 Runloom 事件，业务层不能依赖供应商原始格式。
- 用户可以在 `~/.runloom` 配置默认模型和任务画像模型路由，前端设计、Go 开发、原型设计等任务可以使用不同模型。
- Codex、Claude Code 等外部 agent 是 `ExternalAgentAdapter` / A2A peer，不是普通模型 provider。
- Skills、MCP、A2A、local tools 和自我成长都必须进入统一权限、approval、audit trail、trace 和事件系统。
- 自我演化不能只靠模型自评，必须经过 schema、测试、风险评估和 eval benchmark。
- 高影响变更必须可解释、可审批、可回滚。

## 首期交付范围

首期实现应优先完成 `runloom-agent` 和 `runloom-tui` 的可发布骨架、headless runtime、模型适配接口、工具系统、事件流、todo、session、approval、TUI 最小可用界面和 npm 发布链路，同时为 VSCode 插件预留横向扩展接口。`runloom-web` 先不进入首期实现，保留设计和包边界，后期使用 Vue 3 + TypeScript + Vite 实现。成长层、Tool Forge、Skill Forge、A2A 和 Eval Gate 可以先定义稳定 API 与数据结构，再逐步补全能力。
