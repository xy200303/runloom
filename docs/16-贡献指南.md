# 贡献指南

## 基本原则

Runloom 是本地动态 agent runtime，不是 DAG workflow 引擎。贡献时请保持以下边界：

- agent 逻辑放在 `runloom-agent`。
- TUI/Web 只消费事件和 public API。
- 不新增 WorkflowPatch、workflow version graph、显式 workflow runtime。
- 所有工具、MCP、A2A、外部 agent、自我成长都必须进入权限、approval、audit 和事件系统。
- 产品代码、examples、demo 和文档演示不使用 mock 数据；mock/test-only 数据只允许出现在测试代码、测试 fixtures 或测试 helper 中。
- public API 变更必须有文档、测试和 changelog。

## 开发流程

1. 阅读相关 docs。
2. 确认变更影响的 package。
3. 先补或更新测试。
4. 小范围实现。
5. 更新 README/examples/docs。
6. 运行 typecheck、test、build。
7. 如影响 npm 发布包，添加 changeset。
8. 提交 PR。

## 代码组织与可维护性

Runloom 面向真实长期开发，代码应优先保持清晰、可定位、可测试，而不是追求复杂架构感。新增代码时遵守以下原则：

- 按领域和职责组织文件：runtime、tools、approvals、sessions、providers、TUI commands 等代码放在对应目录，避免把多种职责堆进单个大文件。
- 包边界优先于内部复用：跨 UI、Web、VSCode 的复用应通过 `runloom-agent` public API、host adapter 和事件实现，不通过 import 内部实现共享状态。
- 单个模块只承担一个主要职责；如果一个文件同时处理模型协议、审批、工具执行和 UI 渲染，应拆回对应层。
- 保持依赖方向单向：UI -> public API -> runtime 内部；runtime 不反向依赖 UI，也不读取 UI 私有状态。
- 优先使用本地已有类型、helper 和事件模型，避免为一个小需求创建新的平行类型体系。
- 业务逻辑和展示逻辑分离：TUI/Web/VSCode 可以有视图模型和格式化函数，但不能复制 agent loop、approval policy、tool execution 或 session store。
- 测试替身只能存在于测试代码、fixtures 或 test helper；产品代码不要为了演示或界面好看制造假数据。

## 抽象与耦合

抽象必须服务于明确问题，不为了“看起来可扩展”而提前堆层。

推荐：

- 当两个以上调用点共享稳定语义时，再提取 helper、adapter 或 service。
- 当一段逻辑涉及安全、权限、路径 guard、provider 协议或事件格式时，用明确类型隔离边界。
- 对未来 VSCode/Web 扩展有价值的能力，优先沉到 `runloom-agent` public API 或 host adapter，而不是让某个 UI 包先私有实现一套。
- 小函数、小类型和直接数据流优先；能用清晰参数表达的逻辑，不新增隐式全局状态。

避免：

- 为单一调用点创建过深目录、过多接口或空壳类。
- 把 provider 原始协议、UI 事件、工具输入和 store record 混成一个类型。
- 在 helper 中隐藏审批、安全、文件写入或 shell 执行等高影响行为。
- 让 TUI/Web/VSCode 通过内部路径依赖 runtime 私有结构。
- 为了复用而把无关概念塞进同一个 manager、controller 或 registry。

## 代码风格与注释

代码应简洁直接，变量和函数命名要能表达意图。注释需要足够帮助后续维护者理解上下文，但不要替代码重复显而易见的内容。

注释应该写在这些地方：

- 安全边界：为什么某个操作需要 approval、path guard、redaction 或风险降级。
- 协议转换：供应商事件、OpenAI Responses 语义、Runloom 事件 envelope 之间的映射规则。
- 非显然决策：为什么选择 in-memory、文件存储、adapter 或某个 fallback。
- 未来扩展点：该接口如何给 TUI、Web、VSCode、MCP 或 external agent 复用。
- 错误处理：哪些错误可以恢复，哪些必须失败并进入 event stream。

注释不应该写成：

- 对一行代码的机械翻译。
- 与实际代码不同步的长篇说明。
- 用模糊词掩盖尚未实现的能力。

如果一段代码需要大量注释才能读懂，优先尝试拆分函数、改名、收紧类型或调整模块边界；注释用于解释意图和风险，不替代清晰结构。

## 包边界

允许：

- `runloom-tui` import `runloom-agent` public API。
- `runloom-web` import `runloom-agent` public API。
- 测试使用明确的 testing export，如未来的 `runloom-agent/testing`。

禁止：

- import `runloom-agent/src/internal/*`。
- 在 TUI/Web 中复制 runtime 状态机。
- 在 UI 层直接调用模型 provider。
- 在 UI 层直接执行工具。
- 在 MCP 或外部 agent 中绕过 permission policy。

## Public API

修改 public API 前必须说明：

- 新增、删除还是改变语义。
- 是否 breaking。
- 对相关包 README/examples 的影响。
- 对 event stream 的影响。
- 迁移方式。

事件字段变化尤其谨慎，因为 TUI、Web 和第三方应用都依赖 `RunloomEvent`。

## 测试要求

最低要求：

- 类型测试或编译通过。
- 关键逻辑单元测试，至少覆盖成功路径、失败路径、边界输入和权限分支。
- provider adapter 的测试代码可以使用 recorded fixtures 或 test-only provider，不依赖真实 API。
- tool/security/approval 有负面测试。
- UI 组件至少覆盖事件到视图状态的转换。
- package build 和 pack dry run。

必须优先补充的单元测试：

- `.runloom` 配置 parser、默认值、schema 校验和无效配置报错。
- 全局 `~/.runloom/config.json` 与 workspace `.runloom/config.json` 的合并优先级。
- 模型路由：task profile、language、workspace pattern、默认模型回退和无效 provider。
- provider adapter：输入转换、tool schema 转换、function call output、usage、错误归一化和 metadata。
- runtime：agent loop、todo 状态、event sequence、session store、approval policy、risk decision、path guard。
- tools：每个内置工具的输入校验、workspace 边界、失败结果和权限 scope。
- TUI/Web/VSCode host adapter：命令解析、事件渲染、approval 展示和 API 边界。

必须优先补充的集成测试：

- 使用真实临时 workspace 执行 `submit -> tool call -> tool result -> final output`。
- 使用临时 `stateDir` 验证审批策略、模型配置和 session 数据不会写入用户真实 `~/.runloom`。
- 使用 recorded fixtures、test-only provider 或 local test server 验证 Responses tool call、多 provider 注册和 provider 错误路径。
- TUI 命令覆盖 `/approval`、`/tools`、未来 `/model`，并验证输出来自 `runloom-agent` public API。
- package 级 `build`、`typecheck`、`test`、`pack dry run` 必须覆盖首期发布包。
- 集成测试不得使用产品 mock 数据；测试替身只能存在于测试代码、fixtures 或 test helper。

高影响能力还需要：

- eval benchmark。
- audit trail 检查。
- rollback 测试。
- 手动验收说明。

## 安全要求

以下变更必须额外说明风险：

- 文件写入、删除、移动。
- shell。
- 网络。
- MCP server/client。
- 外部 agent 委托。
- 权限默认值。
- approval policy 模式变更，尤其是 `ask` 改为 `full_access` 或扩大 scope。
- redaction。
- identity/memory。
- self-evolution。
- npm 发布。

禁止把密钥、本地数据库、`~/.runloom` 用户数据或真实私有日志提交到仓库。

## 文档要求

以下变更必须更新文档：

- 新 public API。
- 新 package export。
- 新 provider。
- 新 tool。
- 新 skill manifest 字段。
- 新 MCP/A2A 能力。
- 新 approval 类型。
- 新存储格式。
- 新 CI/release 流程。

## Commit 与 Changeset

建议 commit message 简洁描述用户可见变化，例如：

```text
feat(agent): add model provider interface
fix(tui): render approval denial state
docs: add MCP design
```

影响 npm 包时添加 changeset：

```bash
pnpm changeset
```

## Review 重点

Reviewer 优先看：

- 是否破坏 package 边界。
- 是否泄露 internal API。
- 是否绕过 approval/security/audit。
- provider 协议是否被业务层直接依赖。
- event 类型是否稳定。
- 测试是否覆盖失败路径。
- README/examples 是否同步。

## 本地运行建议

首期建议命令：

```bash
pnpm install
pnpm typecheck
pnpm test
pnpm build
pnpm pack:dry
```

实际命令以根 `package.json` 为准。
