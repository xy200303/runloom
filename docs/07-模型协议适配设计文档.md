# 模型协议适配设计文档

## 目标

Runloom 必须支持四类模型协议：

1. OpenAI-compatible Chat Completions。
2. OpenAI Responses API。
3. Anthropic Claude Messages API。
4. Google Gemini API。

业务层不能直接依赖供应商 API 格式。所有 provider 都必须实现统一 `ModelProvider`，并把 messages、tools、tool calls、streaming events、usage、errors、reasoning 和 structured output 转换成 Runloom 自己的事件和中间类型。

模型输出事件层采用接近 OpenAI Responses API 的 `response.*` 语义。OpenAI Responses adapter 可以近似直连映射；OpenAI-compatible Chat Completions、Anthropic Claude Messages 和 Google Gemini adapter 负责把各自协议转换到同一组 `ModelProviderEvent`。Runloom runtime 再把这些模型输出事件包进完整 `RunloomEvent` envelope，并追加 tool、approval、todo、MCP、A2A、memory、evolution 和 eval 等 runtime 领域事件。

## ModelProvider 接口

建议接口：

```ts
export interface ModelProvider {
  id: string;
  protocol: ModelProtocol;
  capabilities: ModelCapabilities;
  createResponse(request: ModelRequest, context: ModelProviderContext): AsyncIterable<ModelProviderEvent>;
}

export type ModelProtocol =
  | "openai-chat-completions"
  | "openai-responses"
  | "anthropic-messages"
  | "google-gemini"
  | "custom";
```

`ModelRequest` 是 Runloom 内部模型输入：

```ts
export interface ModelRequest {
  model: string;
  input?: RunloomModelInputItem[];
  messages?: RunloomModelMessage[];
  tools?: RunloomModelTool[];
  toolChoice?: "auto" | "none" | { name: string };
  responseFormat?: RunloomResponseFormat;
  maxOutputTokens?: number;
  temperature?: number;
  metadata?: Record<string, string>;
}
```

`model` 字段由 runtime 在进入 provider 前解析完成。provider adapter 不负责根据业务任务选择模型，也不读取 `.runloom` 配置文件。

## 模型选择与任务画像

Runloom 的模型选择属于 runtime 配置层，不属于具体 provider。用户可以在 `~/.runloom/config.json` 配置默认模型和按任务画像划分的模型路由，例如前端设计使用 Kimi 系列模型、Go 开发使用另一个代码模型、原型设计使用更适合快速探索的模型。

建议抽象：

```ts
export interface ModelRoute {
  when: {
    taskType?: "frontend_design" | "go_development" | "prototype_design" | "code_review" | "test_fix";
    language?: string;
    workspacePattern?: string;
  };
  model: string;
}

export interface ModelSelectionResult {
  providerId: string;
  model: string;
  profile?: string;
  reason: string;
}
```

模型选择流程：

1. 读取用户显式指定的 profile 或 model。
2. 合并 workspace `.runloom/config.json` 与全局 `~/.runloom/config.json`。
3. 根据任务类型、主要语言、目录和 host adapter 上下文匹配 route。
4. 找到 `provider:model` 后选择已注册 provider。
5. 发出 `model.selection.resolved` 事件，记录命中规则和选择原因。

provider adapter 只消费最终的 `ModelRequest.model`，并按自身协议转换输入、工具、事件和错误。这样 TUI、后期 Vue Web、VSCode 插件和 CI bot 都可以共享同一套模型路由逻辑。

`ModelProviderEvent` 是 provider 输出：

```ts
export type ModelProviderEvent =
  | { type: "response.created"; responseId?: string }
  | { type: "response.output_text.delta"; delta: string }
  | { type: "response.reasoning.delta"; delta: string }
  | { type: "response.tool_call.delta"; toolCallId: string; name?: string; argumentsDelta?: string }
  | { type: "response.tool_call.completed"; toolCallId: string; name: string; arguments: unknown }
  | { type: "response.structured_output.completed"; value: unknown }
  | { type: "response.usage"; usage: ModelUsage }
  | { type: "response.completed"; finishReason: ModelFinishReason }
  | { type: "response.failed"; error: NormalizedProviderError };
```

runtime 再把这些 provider events 转成 `RunloomEvent`。`response.*` 只表示模型输出层，不代表工具已经执行。例如模型产出 `response.tool_call.completed` 后，runtime 仍要生成 `tool.call.requested`、`approval.requested`、`tool.call.started` 和 `tool.call.completed` 等 Runloom 领域事件。

## 统一消息格式

```ts
export type RunloomModelInputItem =
  | { type: "message"; role: "system" | "user" | "assistant"; content: RunloomContentPart[] }
  | { type: "function_call"; toolCallId: string; name: string; arguments: unknown; raw?: unknown }
  | { type: "function_call_output"; toolCallId: string; output: string };

export type RunloomModelMessage =
  | { role: "system"; content: RunloomContentPart[] }
  | { role: "user"; content: RunloomContentPart[] }
  | { role: "assistant"; content: RunloomContentPart[]; toolCalls?: RunloomToolCall[] }
  | { role: "tool"; toolCallId: string; name: string; content: RunloomContentPart[] };

export type RunloomContentPart =
  | { type: "text"; text: string }
  | { type: "image"; data?: string; url?: string; mimeType?: string }
  | { type: "file"; path?: string; data?: string; mimeType?: string }
  | { type: "redacted"; reason: string };
```

转换原则：

- system/developer 指令在 Runloom 内部统一为 system content，provider adapter 再转换为供应商支持的角色。
- tool result 始终绑定 `toolCallId`。
- 多模态 content 先保持 Runloom 格式，adapter 再决定 base64、URL、file reference 或拒绝。
- redacted content 不应恢复原文。

## 统一 Tool 格式

```ts
export interface RunloomModelTool {
  name: string;
  description: string;
  inputSchema: Record<string, unknown>;
}
```

适配策略：

- OpenAI Chat Completions：映射到 `tools: [{ type: "function", function: ... }]`。
- OpenAI Responses：映射到 Responses tools。
- Claude Messages：映射到 `tools`，JSON schema 需要满足 Anthropic schema 限制。
- Gemini：映射到 function declarations。

所有工具调用参数必须经过 JSON 增量拼接、schema 校验和容错解析。解析失败不直接执行工具，应产生 `ToolCallFailedEvent` 或要求模型重试。

## OpenAI-compatible Chat Completions

输入转换：

- `RunloomModelMessage` 转为 Chat Completions messages。
- tool result 转为 `role: "tool"`。
- tools 转为 function calling。

输出转换：

- `choices[].delta.content` 转为 `response.output_text.delta`。
- `choices[].delta.tool_calls` 按 index 和 id 聚合。
- `usage` 转为 `ModelUsage`。
- `finish_reason` 转为 `ModelFinishReason`。

注意：

- 不同兼容厂商 tool call streaming 细节可能不同，需要 provider options 中支持 compatibility flags。
- 对不支持 reasoning 的模型，reasoning events 为空。
- JSON mode 和 structured output 需要能力检测。

## OpenAI Responses API

输入转换：

- messages 转为 Responses input。
- tools 转为 Responses tools。
- structured output 使用 Responses 支持的 response format 或 tool schema。

输出转换：

- `response.output_text.delta` 转为 Runloom `response.output_text.delta`。
- reasoning item 转为 `response.reasoning.delta` 或 reasoning summary。
- function call item 转为 `response.tool_call.*` events。
- usage 转为统一 usage。

注意：

- Responses API 原生事件更接近 Runloom 模型输出事件层，但仍不能直接作为完整 `RunloomEvent` 外泄。
- OpenAI Responses compatible stream 可以作为 Web/API 的可选投影；内部 store 仍保存 Runloom 自己的 envelope 和 runtime 领域事件。
- `previous_response_id` 是供应商状态能力，Runloom 首期应优先维护自己的 session store，避免被 provider lock-in。

## Anthropic Claude Messages

输入转换：

- system 独立放入 `system` 字段。
- user/assistant content 转为 Claude content blocks。
- tool result 转为 `tool_result`。
- tools 转为 Claude tool schema。

输出转换：

- `content_block_delta` text 转为 `response.output_text.delta`。
- `thinking_delta` 或等价 reasoning 转为 `response.reasoning.delta`，前提是配置允许。
- `tool_use` content block 转为 `response.tool_call.*`。
- stop reason 转为统一 finish reason。

注意：

- Claude 对 tool result 的结构和 content block 顺序较严格。
- reasoning/thinking 内容可能受供应商策略限制，必须支持不可用状态。
- 多模态输入需要按 Claude 支持的 image block 转换。

## Google Gemini

输入转换：

- messages 转为 contents。
- system 指令转为 systemInstruction。
- tools 转为 functionDeclarations。
- tool result 转为 functionResponse。

输出转换：

- candidate parts 中 text 转为 `response.output_text.delta`。
- functionCall 转为 `response.tool_call.completed`。
- usage metadata 转为统一 usage。
- finishReason 转为统一 finish reason。

注意：

- Gemini 的 role 和 part 语义与 OpenAI/Claude 不完全一致，必须在 adapter 中隔离。
- function response 的格式要与 function call name 对应。
- structured output 可使用 response schema 或 tool-based fallback。

## Usage 统一

```ts
export interface ModelUsage {
  inputTokens?: number;
  outputTokens?: number;
  reasoningTokens?: number;
  cachedInputTokens?: number;
  totalTokens?: number;
  raw?: unknown;
}
```

UI 只读取统一字段。`raw` 只用于 debug trace，不应在默认事件流中外发。

## Error 统一

```ts
export interface NormalizedProviderError {
  code: string;
  message: string;
  provider: string;
  retryable: boolean;
  statusCode?: number;
  rateLimited?: boolean;
  authenticationFailed?: boolean;
  contextWindowExceeded?: boolean;
  raw?: unknown;
}
```

错误分类：

- authentication。
- rate limit。
- network。
- timeout。
- context window。
- invalid request。
- content safety。
- provider unavailable。
- unknown。

## Capabilities

```ts
export interface ModelCapabilities {
  streaming: boolean;
  tools: boolean;
  parallelToolCalls?: boolean;
  reasoning?: boolean;
  structuredOutput?: boolean;
  vision?: boolean;
  files?: boolean;
  maxInputTokens?: number;
  maxOutputTokens?: number;
}
```

runtime 根据 capabilities 做降级：

- 无 tools：使用文本计划和宿主工具禁用提示。
- 无 structured output：用 tool-based JSON schema fallback。
- 无 vision：拒绝图片输入或转交外部工具提取文本。
- context 过长：触发 context compression。

## 测试策略

每个 adapter 必须有：

- message conversion snapshot tests。
- `RunloomModelInputItem` 到供应商输入结构的 conversion tests。
- tool schema conversion tests。
- streaming event parser tests。
- malformed tool arguments tests。
- usage normalization tests。
- provider error normalization tests。
- capability fallback tests。
- model request metadata 透传测试。

模型选择层必须有：

- 全局 `~/.runloom/config.json` parser 单元测试。
- workspace `.runloom/config.json` 覆盖全局配置的 merge 测试。
- task profile、language、workspace pattern 的 route matching 测试。
- route miss 回退到默认模型的测试。
- 未注册 provider、无效模型标识和缺失 secret 的错误归一化测试。
- `model.selection.resolved` 事件内容测试，确保不记录 API key 或 secret。

集成测试必须覆盖：

- 使用 test-only provider 执行一次按 profile 选择模型的完整 `submit`。
- 使用 recorded fixture 或 local test server 覆盖 Responses function tool call 循环。
- 多 provider 注册后，前端设计、Go 开发、原型设计三类任务分别命中不同模型。
- provider 不可用时的失败事件、错误消息和 run status。

测试代码可以提供 recorded stream fixtures、test-only provider 或 local test server，避免 CI 依赖真实供应商。产品 runtime、examples 和 demo 不使用 mock 数据。
