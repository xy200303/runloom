# 贡献指南

## 基本原则

Runloom 是本地动态 agent runtime，不是 DAG workflow 引擎。贡献时请保持以下边界：

- agent 逻辑放在 `runloom-agent`。
- TUI/Web 只消费事件和 public API。
- 不新增 WorkflowPatch、workflow version graph、显式 workflow runtime。
- 所有工具、MCP、A2A、外部 agent、自我成长都必须进入权限、approval、audit 和事件系统。
- 产品代码、examples、demo 和文档演示不使用 mock 数据；mock/test-only 数据只允许出现在测试代码、测试 fixtures 或测试 helper 中。
- public API 变更必须有文档、测试和 changelog。

## 开发流程

1. 阅读相关 docs。
2. 确认变更影响的 package。
3. 先补或更新测试。
4. 小范围实现。
5. 更新 README/examples/docs。
6. 运行 typecheck、test、build。
7. 如影响 npm 发布包，添加 changeset。
8. 提交 PR。

## 包边界

允许：

- `runloom-tui` import `runloom-agent` public API。
- `runloom-web` import `runloom-agent` public API。
- 测试使用明确的 testing export，如未来的 `runloom-agent/testing`。

禁止：

- import `runloom-agent/src/internal/*`。
- 在 TUI/Web 中复制 runtime 状态机。
- 在 UI 层直接调用模型 provider。
- 在 UI 层直接执行工具。
- 在 MCP 或外部 agent 中绕过 permission policy。

## Public API

修改 public API 前必须说明：

- 新增、删除还是改变语义。
- 是否 breaking。
- 对相关包 README/examples 的影响。
- 对 event stream 的影响。
- 迁移方式。

事件字段变化尤其谨慎，因为 TUI、Web 和第三方应用都依赖 `RunloomEvent`。

## 测试要求

最低要求：

- 类型测试或编译通过。
- 关键逻辑单元测试，至少覆盖成功路径、失败路径、边界输入和权限分支。
- provider adapter 的测试代码可以使用 recorded fixtures 或 test-only provider，不依赖真实 API。
- tool/security/approval 有负面测试。
- UI 组件至少覆盖事件到视图状态的转换。
- package build 和 pack dry run。

必须优先补充的单元测试：

- `.runloom` 配置 parser、默认值、schema 校验和无效配置报错。
- 全局 `~/.runloom/config.json` 与 workspace `.runloom/config.json` 的合并优先级。
- 模型路由：task profile、language、workspace pattern、默认模型回退和无效 provider。
- provider adapter：输入转换、tool schema 转换、function call output、usage、错误归一化和 metadata。
- runtime：agent loop、todo 状态、event sequence、session store、approval policy、risk decision、path guard。
- tools：每个内置工具的输入校验、workspace 边界、失败结果和权限 scope。
- TUI/Web/VSCode host adapter：命令解析、事件渲染、approval 展示和 API 边界。

必须优先补充的集成测试：

- 使用真实临时 workspace 执行 `submit -> tool call -> tool result -> final output`。
- 使用临时 `stateDir` 验证审批策略、模型配置和 session 数据不会写入用户真实 `~/.runloom`。
- 使用 recorded fixtures、test-only provider 或 local test server 验证 Responses tool call、多 provider 注册和 provider 错误路径。
- TUI 命令覆盖 `/approval`、`/tools`、未来 `/model`，并验证输出来自 `runloom-agent` public API。
- package 级 `build`、`typecheck`、`test`、`pack dry run` 必须覆盖首期发布包。
- 集成测试不得使用产品 mock 数据；测试替身只能存在于测试代码、fixtures 或 test helper。

高影响能力还需要：

- eval benchmark。
- audit trail 检查。
- rollback 测试。
- 手动验收说明。

## 安全要求

以下变更必须额外说明风险：

- 文件写入、删除、移动。
- shell。
- 网络。
- MCP server/client。
- 外部 agent 委托。
- 权限默认值。
- approval policy 模式变更，尤其是 `ask` 改为 `full_access` 或扩大 scope。
- redaction。
- identity/memory。
- self-evolution。
- npm 发布。

禁止把密钥、本地数据库、`~/.runloom` 用户数据或真实私有日志提交到仓库。

## 文档要求

以下变更必须更新文档：

- 新 public API。
- 新 package export。
- 新 provider。
- 新 tool。
- 新 skill manifest 字段。
- 新 MCP/A2A 能力。
- 新 approval 类型。
- 新存储格式。
- 新 CI/release 流程。

## Commit 与 Changeset

建议 commit message 简洁描述用户可见变化，例如：

```text
feat(agent): add model provider interface
fix(tui): render approval denial state
docs: add MCP design
```

影响 npm 包时添加 changeset：

```bash
pnpm changeset
```

## Review 重点

Reviewer 优先看：

- 是否破坏 package 边界。
- 是否泄露 internal API。
- 是否绕过 approval/security/audit。
- provider 协议是否被业务层直接依赖。
- event 类型是否稳定。
- 测试是否覆盖失败路径。
- README/examples 是否同步。

## 本地运行建议

首期建议命令：

```bash
pnpm install
pnpm typecheck
pnpm test
pnpm build
pnpm pack:dry
```

实际命令以根 `package.json` 为准。
