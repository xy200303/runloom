# 自我演化机制设计文档

## 定位

自我演化是 Runloom 对自身能力的受控改进流程。它可以分析自身、提出改进、修改代码、运行测试、评估结果，并在验证通过和必要确认后升级。

自我演化不是：

- 静默改写自身代码。
- 只靠模型自评。
- 自动扩大权限。
- 自动修改身份文件。
- 绕过 CI 或 eval gate 的快速路径。

## 状态机

```text
observed
  -> proposed
  -> planned
  -> implemented
  -> validated
  -> evaluated
  -> approved
  -> accepted
```

失败或拒绝分支：

```text
proposed/planned/implemented/validated/evaluated
  -> rejected
  -> archived
```

回滚分支：

```text
accepted
  -> rollback_requested
  -> rolled_back
```

## Evolution Proposal

```ts
export interface EvolutionProposal {
  id: string;
  title: string;
  kind: "prompt" | "identity" | "tool" | "skill" | "code" | "policy" | "eval";
  reason: string;
  evidence: string[];
  expectedBenefit: string;
  risks: string[];
  affectedFiles: string[];
  requiredApprovals: string[];
  validationPlan: ValidationPlan;
  rollbackPlan: RollbackPlan;
}
```

proposal 存储：

```text
~/.runloom/evolution/proposals/<proposal-id>/
  proposal.json
  rationale.md
  evidence.json
  risk.md
  rollback.md
```

## 代码修改计划

代码级演化必须先生成 plan：

```ts
export interface CodeModificationPlan {
  proposalId: string;
  scope: string[];
  intendedChanges: string[];
  publicApiImpact: "none" | "minor" | "breaking";
  testsToRun: string[];
  evalsToRun: string[];
  rollback: string[];
}
```

要求：

- 明确范围，不做无关重构。
- 标记 public API 影响。
- 标记安全策略影响。
- 标记数据迁移影响。
- 修改前记录 baseline。

## 验证流程

验证分层：

1. Schema validation：proposal、tool、skill、config、benchmark。
2. Static checks：typecheck、lint、dependency constraints。
3. Unit tests。
4. Integration tests。
5. Security checks：权限、路径、命令、secret redaction。
6. Eval benchmark：baseline vs candidate。
7. Human approval：高影响变更。

任何一层失败都不能进入 accepted。

## Eval Gate

自我演化必须跑 eval benchmark：

- 项目理解。
- 工具调用。
- 文件修改。
- 测试修复。
- 记忆总结。
- 权限遵守。
- 危险操作拒绝。
- 本地工具生成。
- 用户偏好遵守。
- 多 agent 协作。
- Skills 使用。
- MCP 调用。

通过条件：

- candidate score 不低于 baseline。
- 关键安全项必须全通过。
- 失败项有解释和风险处理。
- 高影响变更需要用户 approval。

## Accepted / Rejected

accepted 记录：

```text
~/.runloom/evolution/accepted/<proposal-id>/
  proposal.json
  diff.patch
  validation.json
  eval-report.json
  approval.json
  rollback.md
```

rejected 记录：

```text
~/.runloom/evolution/rejected/<proposal-id>/
  proposal.json
  reason.md
  validation.json
  eval-report.json
```

Rejected 不代表丢失，它是未来学习材料。

## 升级策略

Runloom 自我升级分三种：

- `runtime-local-state`：修改 `~/.runloom` 下的 skill/tool/memory/prompt。
- `project-code`：修改当前项目代码。
- `package-release`：修改 Runloom 自身包版本并发布。

`package-release` 风险最高，必须：

- 通过完整 CI。
- 通过 eval gate。
- 更新 changelog。
- bump version。
- 用户确认发布。
- 保留 rollback tag。

## 回滚策略

每个 accepted 结果必须有 rollback：

- 文件 patch 反向应用。
- 工具/skill 禁用或回退版本。
- identity 文件恢复到前一个 hash。
- npm package 回退到上一个版本。
- memory 标记为 rejected 或 expired。

回滚本身也产生 audit trail。

## Approval 规则

必须审批：

- 修改 `soul.md`、`thinking.md`。
- 注册新工具。
- 注册新 skill。
- 修改自身代码。
- 修改发布配置。
- 扩大权限。
- 发布 npm 包。
- 删除长期记忆。

可配置为自动：

- 低风险 docs 修正。
- 非关键 lessons candidate。
- 已批准范围内的测试 fixture 更新。

## Audit Trail

每次演化记录：

- 来源。
- 证据。
- 变更原因。
- 受影响文件。
- 风险。
- approval。
- 测试日志。
- eval baseline/candidate。
- 最终状态。
- 回滚方式。

## 防护原则

- 默认保守。
- 权限扩大永远高风险。
- 模型建议不等于事实。
- eval gate 不能被 proposal 自己修改后立即信任，benchmark 更新也需要审查。
- 自我演化不能在用户明确要求只做普通任务时偷偷运行高影响修改。
