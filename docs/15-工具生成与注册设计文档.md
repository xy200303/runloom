# 工具生成与注册设计文档

## 定位

Tool Forge 让 Runloom 在发现重复任务或能力缺口时，生成本地工具包，并在验证和审批后注册为可调用工具。工具生成是高影响成长能力，必须经过 schema、测试、权限、风险和 eval gate。

## 本地目录

```text
~/.runloom/
  tools/
    local-tools/
      <tool-name>/
        tool.json
        tool.ts
        README.md
        tests/
        package.json
```

首期可不要求每个本地工具都是独立 npm 包，但目录结构应为未来发布或共享预留。

## tool.json

示例：

```json
{
  "name": "summarize-package-json",
  "version": "0.1.0",
  "description": "Read and summarize a package.json file.",
  "entry": "tool.ts",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": { "type": "string" }
    },
    "required": ["path"],
    "additionalProperties": false
  },
  "permissions": {
    "filesystem": "read",
    "shell": "deny",
    "network": "deny"
  },
  "timeoutMs": 30000
}
```

## ToolDefinition

运行时工具接口：

```ts
export interface ToolDefinition<TInput = unknown, TOutput = unknown> {
  name: string;
  description: string;
  inputSchema: Record<string, unknown>;
  permissions: ToolPermissionSpec;
  execute(input: TInput, context: ToolContext): Promise<TOutput>;
}
```

`ToolContext` 提供：

- workspace。
- allowed roots。
- logger。
- trace。
- redactor。
- abort signal。
- store。
- approval helpers。

工具不应直接读取全局配置或绕过 context。

## 生成触发

Tool Forge 候选来源：

- 多次重复 shell/file 操作。
- reflection 识别稳定步骤。
- 用户明确要求“做成工具”。
- eval 发现某类任务失败，且工具化能降低风险。
- skill 使用中出现固定可验证步骤。

生成前必须回答：

- 这个能力是否真的需要工具，而不是 skill 或 prompt？
- 是否已有内置工具或 MCP 工具能完成？
- 工具是否可测试？
- 工具是否会扩大权限？
- 输出是否能结构化？

## 生成流程

```text
detect candidate
  -> create tool proposal
  -> draft tool.json/tool.ts/README/tests
  -> schema validation
  -> static analysis
  -> unit tests
  -> permission analysis
  -> sandbox execution
  -> eval gate if high impact
  -> approval
  -> register tool
  -> write audit
```

## Proposal

```ts
export interface ToolForgeProposal {
  id: string;
  toolName: string;
  reason: string;
  evidence: string[];
  expectedUseCases: string[];
  permissions: ToolPermissionSpec;
  files: GeneratedToolFile[];
  validationPlan: ValidationPlan;
  risk: RiskAssessment;
  rollbackPlan: RollbackPlan;
}
```

## 权限

权限维度：

- filesystem：none/read/write/delete。
- shell：deny/ask/allow。
- network：deny/ask/allow。
- environment：deny/allowlist。
- mcp：deny/ask/allow。
- externalAgents：deny/ask/allow。

默认：

- shell deny。
- network deny。
- delete deny。
- environment deny。
- workspace 外路径 deny。

权限扩大必须单独 approval。

## 验证

必须验证：

- `tool.json` schema。
- `inputSchema` 严格，默认 `additionalProperties: false`。
- TypeScript typecheck。
- 单元测试。
- 工具 timeout。
- abort signal。
- path guard。
- redaction。
- 输出 JSON 可序列化。

高影响工具还需：

- eval benchmark。
- malicious input tests。
- rollback test。
- manual approval。

## 注册

注册状态：

- `draft`：生成但未验证。
- `validated`：本地验证通过。
- `pending_approval`：等待用户确认。
- `registered`：可被 runtime 调用。
- `disabled`：用户禁用。
- `rejected`：未通过或被拒绝。

注册时：

- 写入 registry。
- 记录 hash。
- 绑定权限。
- 产生 `tool.registered` 事件。
- 写入 audit trail。

## 运行

本地工具执行必须仍走统一 ToolExecutor：

```text
model tool call
  -> schema validation
  -> permission policy
  -> approval if needed
  -> execute local tool
  -> timeout/abort
  -> redaction
  -> result normalization
  -> audit
  -> event
```

即使是 Runloom 自己生成的工具，也不能绕过安全层。

## README 要求

每个工具 README 包含：

- 用途。
- 输入 schema。
- 输出格式。
- 权限说明。
- 示例。
- 测试命令。
- 风险和限制。
- 回滚方式。

## 回滚

回滚方式：

- 禁用工具。
- 恢复上一版本。
- 删除 registry entry。
- 移动到 rejected。
- 记录原因。

如果工具已被某些 memories 或 skills 引用，需要标记引用失效。

## 与 Skill Forge 的关系

Tool Forge 生成“可执行能力”。Skill Forge 生成“使用方法和流程”。

常见组合：

- 先生成工具，再生成 skill 说明何时使用。
- 先有 skill，发现步骤稳定后提取成工具。
- 工具验证失败时，可先退回 skill 或文档流程。
