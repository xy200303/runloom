# 本地成长层设计文档

## 定位

Runloom 的本地成长层让 agent 能在用户本地长期协作、沉淀经验、学习偏好、总结教训，并提出工具、skill 或身份策略改进。成长层不是隐式魔法，也不是静默改写，而是一组可审计、可审批、可回滚的本地状态。

## 目录结构

```text
~/.runloom/
  identity/
    soul.md
    thinking.md
    user-preferences.md
    lessons.md
  memories/
    episodic/
    semantic/
  tools/
    local-tools/
      <tool-name>/
        tool.json
        tool.ts
        README.md
        tests/
  skills/
    installed/
    generated/
  mcp/
    servers.json
  a2a/
    peers.json
  evals/
    benchmarks/
    runs/
  evolution/
    runs/
    proposals/
    accepted/
    rejected/
```

首次启动时，Runloom 应创建目录和默认文件，但不覆盖用户已有内容。

## Identity 文件

| 文件 | 作用 | 修改策略 |
| --- | --- | --- |
| `soul.md` | Runloom 的长期定位、原则、自我描述 | 只能通过 proposal 和用户 approval 修改 |
| `thinking.md` | 思维方式、做事方法、沟通风格、协作策略 | 高影响修改需要 approval |
| `user-preferences.md` | 用户偏好、沟通习惯、项目习惯、长期约定 | 可提出增量更新，默认需要用户确认 |
| `lessons.md` | 失败教训、修正经验、可复用原则 | 可追加 proposal，经验证后写入 |

identity 文件进入上下文时需要：

- 按任务相关性选择。
- 做上下文预算。
- 标记来源。
- 防止 prompt injection。
- 记录引用版本或 hash。

## Episodic Memory

Episodic memory 记录具体经历。

示例：

```json
{
  "id": "mem_ep_001",
  "type": "episodic",
  "timestamp": "2026-06-05T10:00:00.000Z",
  "sessionId": "ses_123",
  "runId": "run_456",
  "summary": "用户要求规划 Runloom 文档，最终生成 docs 设计文档。",
  "evidence": ["docs/01-技术设计文档.md"],
  "tags": ["docs", "architecture", "runloom"],
  "retention": "candidate"
}
```

规则：

- 不是每次任务都永久保留。
- 默认先进入 candidate。
- 经过 curation 后才可转入 retained 或 distilled。
- 包含 secret、私人信息或临时噪声的记忆需要 redaction 或丢弃。

## Semantic Memory

Semantic memory 记录从经历中提炼出的稳定知识。

示例：

```json
{
  "id": "mem_sem_001",
  "type": "semantic",
  "statement": "该用户偏好先做设计文档，再进入实现。",
  "sourceEpisodes": ["mem_ep_001", "mem_ep_004"],
  "confidence": 0.82,
  "lastValidatedAt": "2026-06-05T10:00:00.000Z",
  "tags": ["user-preference", "planning"]
}
```

规则：

- 必须能追溯到 episodic evidence。
- confidence 低时只能作为候选，不进入强指令。
- 与用户显式指令冲突时，用户当前指令优先。
- 长期未验证的 semantic memory 需要衰减或复核。

## Reflection

每次任务结束后可运行 reflection：

```text
collect run summary
  -> identify what worked
  -> identify what failed
  -> identify reusable lesson
  -> propose memory candidates
  -> propose preference updates
  -> propose skill/tool/evolution candidates
```

Reflection 输出：

```ts
export interface ReflectionResult {
  runId: string;
  workedWell: string[];
  wentPoorly: string[];
  nextTime: string[];
  memoryCandidates: MemoryCandidate[];
  lessonCandidates: LessonCandidate[];
  skillCandidates: SkillCandidate[];
  toolCandidates: ToolCandidate[];
}
```

约束：

- reflection 不自动修改高影响文件。
- reflection 不是 eval，不能替代 benchmark。
- reflection 内容需要 redaction。
- 用户可以禁用或限制 reflection。

## Memory Curation

Memory curation 负责把具体经历筛选成长期经验，避免无意义记忆污染上下文。

筛选标准：

- 是否可复用。
- 是否有证据。
- 是否稳定。
- 是否与已有 memory 重复。
- 是否包含敏感信息。
- 是否过期。
- 是否与用户显式偏好冲突。

状态：

- `candidate`：候选。
- `retained`：保留为 episodic。
- `distilled`：提炼为 semantic。
- `rejected`：丢弃。
- `expired`：过期。

## 用户偏好学习

偏好来源：

- 用户显式表达。
- 多次相同行为反馈。
- 用户纠正 Runloom 的方式。
- 项目长期约定。

偏好更新必须带证据：

```ts
export interface PreferenceUpdateProposal {
  id: string;
  statement: string;
  evidence: string[];
  confidence: number;
  targetFile: "user-preferences.md";
  diff: string;
}
```

低风险偏好可在 TUI/Web 中批量确认。涉及隐私、安全、身份或权限的偏好需要单独 approval。

## Lessons

`lessons.md` 记录失败教训和修正原则。写入要求：

- 有失败或反馈证据。
- 能复用到未来任务。
- 不只是一次性事实。
- 不包含 secret。
- 不与更高优先级策略冲突。

示例条目：

```md
## 2026-06-05：文档优先任务不要提前实现

来源：用户明确要求“请先不要直接实现完整代码”。
原则：当用户要求先规划或设计文档时，先完成文档和验收标准，不创建功能实现。
```

## 上下文选择

任务开始时 runtime 会选择成长上下文：

1. 当前用户目标。
2. workspace/project signals。
3. active skills。
4. user preferences。
5. relevant semantic memory。
6. recent episodic memory。
7. identity/thinking 片段。

选择结果需要产生内部 trace，便于解释“为什么 Runloom 记得这件事”。

## Approval

需要 approval：

- 修改 `soul.md`。
- 修改 `thinking.md`。
- 修改 `user-preferences.md`。
- 修改 `lessons.md`。
- 新增 generated skill。
- 注册 generated tool。
- 删除 memory。
- 扩大 memory 可见范围。

用户可以配置自动审批低风险 memory，但默认高影响成长需要确认。

## 隐私与安全

要求：

- secret redaction。
- memory encryption 可作为后续增强。
- 支持导出和删除用户数据。
- 支持禁用成长层。
- 支持项目级隔离。
- 支持 memory retention policy。

## TUI/Web 展示

UI 需要展示：

- 本地成长状态。
- 最近 reflection。
- memory candidates。
- preference update proposals。
- identity update proposals。
- accepted/rejected 记录。
- 回滚入口。

UI 不直接编辑 `~/.runloom` 文件，应通过 `runloom-agent` API 提交 approval 或 proposal。
